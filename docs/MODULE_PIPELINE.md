# 模块流水线

每个补丁独立走完下面五步，再开下一个。范例是 `synia:debugify`（tag `synia-debugify-0.1.0`，实测记录在 [VERIFICATION.md](VERIFICATION.md) 第 5 节）。

判定细则和失败分支以 [VERIFICATION.md](VERIFICATION.md) 为准。加载成功不等于门控生效。

## 1. 选题门槛

技术上同时满足才进入实现：

- 有明确、可门控的入口（配置文件、单个 Mixin、单个缺失类）。
- 失败原因单一，能用一句话说清。

开工时机见 [ROADMAP.md](ROADMAP.md)：任意两条触发条件成立后才进入这里。入口不明确的，报告再多也不开工。

## 2. 时序证据

通用原则只有一条：本模块的动作必须早于目标模组的预加载，或早于它做出不可逆决策的那一刻。日志前缀随模块变化。没有 `service_ts` 这一行，只说明这次用的不是 Debugify 那种日志名。

`synia:debugify` 是「写配置文件」门控，它的具体证据是：

1. `service_ts`：early service 已被加载。
2. `write_ts_end` 与 `disk_audit=PASS`：写入完成，落盘内容就是预期值。`disk_audit=PASS` 只属于这种门控。字节码转换或类加载拦截没有这一检查点。
3. `write_ts_end` 早于目标模组自己的预加载日志（或等价证据，例如它打印的「已启用修复」列表）。

`disk_audit=PASS` 只在审计路径与目标模组实际读取的路径一致时成立。Debugify 读的是 `config/debugify.json`，审计也是这个文件。若门控写的是子目录或其他位置，审计跟着那条路径走。

缺了本门控形式所要求的证据，停在这一层，不要做行为对照。

## 3. 行为对照

同一操作、同一世界，做三组：

| 组 | 条件 |
|----|------|
| A | 门控开启 |
| B | 杀开关打开，jar 仍在 |
| C | 完全移除本模块 jar |

通过标准：**A ≠ B，且 B ≈ C**。靶点行为必须能复现，每人用一句话记下。

B ≈ C 必须实测。杀开关「逻辑上不写配置」不能代替把 jar 拿掉再启动一次。

## 4. 回归

关掉杀开关，把 jar 放回去，再启动一次。行为必须回到组 A。写配置的模块还要再次看到 `disk_audit=PASS`，且审计的仍是目标模组实际读取的那个文件。

## 5. 失败分层

先定层，再决定要不要做 companion / Jar-in-Jar。

| 层 | 看到什么 |
|----|----------|
| 加载 | 没有本模块的加载证据（Debugify 范例：没有 `service_ts`） |
| 时序 | 本模块的动作晚于目标模组预加载（Debugify 范例：`write_ts_end` 更晚） |
| 路径 | 审计失败，或审计的文件不是目标模组实际读取的那个 |
| 缓存 | 日志和磁盘都对，但行为对照里修复仍按旧状态生效 |

只有「时序」或「缓存」证明配置写入赶不上、或写了也不被采用时，才考虑 companion / Jar-in-Jar。不要在未定层时换方案。

## 完成定义

五步都有日志或一句话观察，并写进 [VERIFICATION.md](VERIFICATION.md)。然后给该模块的版本打 tag。未完成的模块保持未闭环，不拿它当下一个模块的基准。
